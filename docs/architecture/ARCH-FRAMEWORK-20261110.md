# Scalable architecture framework

Status: Draft / Proposed. Researched 10 November 2026, Australia/Sydney (AEDT).
Scope: Grok Bot shared box, Cursor CLI/cloud agents; GitHub or Cursor Origin.
Draft only. No deployment, paid API adoption, git index staging or external changes.

**Reading rule:** linked facts describe the fetched sources. “Proposed policy” means our design choice, not a vendor guarantee. Examples and tests are specifications, not implemented results. Optimise measured constraints; do not buy complexity on spec. AWS and Azure both frame architecture as explicit quality/cost trade-offs, not a universal stack. [AWS framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html); [Azure framework](https://learn.microsoft.com/en-us/azure/well-architected/what-is-well-architected-framework).

## 1. Requirements and constraints

- **Facts:** an SLI is a quantitative service measure; an SLO is its target/range. Error budgets balance reliability and change velocity. [Google SRE: SLOs](https://sre.google/sre-book/service-level-objectives/); [Google SRE: risk](https://sre.google/sre-book/embracing-risk/).
- **Proposed policy:** record users, peak/steady load, latency percentiles, freshness, data sensitivity, failure tolerance, recovery targets and a cost ceiling before choosing components. Review security, reliability, performance, operations and cost together; include AWS's sustainability perspective. Do not present cloud-specific guidance as a portability guarantee. [AWS](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html); [Azure](https://learn.microsoft.com/en-us/azure/well-architected/what-is-well-architected-framework).
- **Gate:** owner agrees the measurement window, good/eligible-event definition, exclusions and budget response. Example only: a 99.9% success SLO allows 0.1% bad eligible events over that window; targets remain undecided. Escalate reliability work when the agreed budget is exhausted. [SLI definition](https://sre.google/sre-book/service-level-objectives/); [Budget control loop](https://sre.google/sre-book/embracing-risk/).

## 2. Boundaries

- **Facts:** a monolithic app normally deploys as a single unit; logical separation still helps non-trivial apps. **Proposed policy for NEW services/new deploy units only:** consider one modular monolith, one primary database and capability-owned interfaces; split deployment only for measured isolation, ownership or scaling need. Existing systems conform through documented applicability exceptions and accepted ADRs, not forced topology changes. This is a starting hypothesis, not a rule that monoliths always win. [Microsoft architecture guide](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures).
- **Existing-topology exceptions (binding for this bundle):** ModMe is a federated dual-monorepo: preserve `next-forge/` (Bun) and `GenerativeUI_monorepo/` (Yarn); “This repository contains **independent monorepos**. Do not merge them.” Do not add cross-monorepo `workspace:*` dependencies. Preserve accepted ADR-0010's GreptimeDB `code_index` + Supabase `inbox_entries`, synchronised only at promote; this framework is not authority to collapse either store. [ModMe monorepo rule](/workspace/modme-ui-01/.cursor/rules/monorepo-boundaries.mdc#L8); [ModMe accepted ADR-0010](/workspace/modme-ui-01/next-forge/docs/adr/0010-dual-store-knowledge-intake.md#L3).
- **Tooling-kit exception:** `thunderstone-starter` is Drive-first tooling with `scripts/` and `.cursor/hooks/`, and no `src/` directory in the inspected tree; do not invent a product-monolith folder layout for it. Drive remains the authoring/intelligence workspace; GitHub owns promoted active code. [Starter AGENTS.md](/workspace/thunderstone-starter/AGENTS.md#L3); [local starter tree](/workspace/thunderstone-starter/).
- **Proposed policy:** modules own their writes and expose small APIs; no cross-module table writes or private imports. For NEW systems draw C4 system-context/container views first; for ModMe maintain the existing [C4 context](/workspace/modme-ui-01/C4-Documentation/c4-context.md) and [container](/workspace/modme-ui-01/C4-Documentation/c4-container.md) views rather than replacing them. Add component views only where useful. C4's containers are architectural abstractions, not a demand for Docker or microservices. [C4 official model](https://c4model.com/); [C4 container definition](https://c4model.com/abstractions/container); [Logical separation](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures).
- **Gate:** record consequential choices, alternatives and consequences in one ADR per decision. This bundle's hosting ADR is [ADR-0002](ADR-0002-code-host-origin-vs-github-20261110.md), still Proposed and numbered **only against `/workspace/thunderstone/drafts/`**. ModMe's `docs/adr/` and `next-forge/docs/adr/` are separate inventories; choose the owning inventory before assigning a number. [ADR definition](https://adr.github.io/); [Nygard format](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions).

## 3. Contracts first

- **Facts:** OpenAPI describes HTTP API interfaces; the pinned OAS 3.1.1 Schema Object builds on JSON Schema 2020-12. JSON Schema supplies structural validation vocabulary. Neither is proof of business authorisation. [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html); [JSON Schema validation](https://json-schema.org/draft/2020-12/json-schema-validation.html).
- **Proposed policy:** version boundary contracts and fixtures before implementation. OAS/JSON Schema is one option for HTTP/schema interchange, not a compulsory rewrite. Accept existing Zod + Pydantic + golden JSON as the contract source of truth where parity/version/negative fixtures are maintained. ModMe already documents shared golden-fixture parsing in both language stacks; starter has no OAS migration requirement. Record the contract-to-boundary mapping or explicit applicability waiver, retaining existing schema owners. [ModMe contract-parity architecture](/workspace/modme-ui-01/docs/codebase/ARCHITECTURE.md#L53); [Zod parsing](https://zod.dev/basics); [Pydantic JSON validation](https://docs.pydantic.dev/latest/concepts/models/).
- **Binding runtime constraint:** validate against the approved endpoint/model and pinned router/validator versions, not another provider's feature table. LiteLLM documents per-model `get_supported_openai_params` / `supports_response_schema` checks and optional client-side JSON Schema validation; supported format, keywords and failure handling need endpoint-specific fixtures. xAI limits here are reference-only, not automatically inherited by LiteLLM routes. No new paid API or endpoint is authorised. [LiteLLM structured-output support](https://docs.litellm.ai/docs/completion/json_mode).
- **Boundary policy:** Validate inbound requests, queue events, external responses and model output before side effects. Apply independent permission, domain-invariant and size checks. Example event envelope: `schemaVersion`, `eventId`, `kind`, `payload`; these names are local convention. [HTTP contracts](https://spec.openapis.org/oas/v3.1.1.html); [Structural constraints](https://json-schema.org/draft/2020-12/json-schema-validation.html); [Model schema limits](https://docs.x.ai/developers/model-capabilities/text/structured-outputs).
- **Gate:** positive/negative fixtures, malformed payload rejection and compatibility tests; repeated event IDs must not repeat a write. Contract-first pattern: [boundary validation](PATTERN-contract-first-boundary-validation-20261110.md). Idempotency is a separate persistence guarantee, not a schema feature. [AWS idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).

## 4. Data and state

- **Proposed policy:** designate one authoritative owner/store per business fact; for NEW services start with one database, explicit transactions and a restore test. Existing accepted storage topology wins: ModMe retains ADR-0010's dual-store; define an owner per fact rather than collapsing stores. [ModMe accepted ADR-0010](/workspace/modme-ui-01/next-forge/docs/adr/0010-dual-store-knowledge-intake.md#L3). Keep durable checkpoints and deduplication records outside worker memory. Twelve-factor stateless processes persist through backing services; this does not mean databases themselves are stateless. [Processes](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/processes.md); [Attached resources](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/backing-services.md).
- **Proposed policy:** store the caller/event token and mutation result atomically; return the recorded result on a matching retry, reject token reuse with different intent. Set retention from actual retry/replay windows. Do not promise exactly-once network delivery. [Request identity, atomicity and intent](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).
- **Gate:** kill/restart/replay tests preserve acknowledged writes and do not duplicate effects. The box's persistent filesystem is an authoring workspace, not automatic distributed coordination; cloud agents run in isolated VMs, not the box's filesystem. Export bounded artifacts and use explicit storage/locking when work crosses runtimes. [Disposability](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/disposability.md); [Cloud runtime](https://cursor.com/docs/cloud-agent.md).

## 5. Scaling path — adapted twelve-factor basis

Basis: [TWELVE-FACTOR-AGENTS-20261110.md](TWELVE-FACTOR-AGENTS-20261110.md), adapted from the pinned CC BY 4.0 upstream repository, not an assertion of universal compliance. The upstream README describes an updated manifesto distinct from the original site. [Upstream provenance](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/README.md); [Licence](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/LICENSE); [Original methodology](https://12factor.net/).

**Proposed sequence, not an upstream prescription:** stateless runtime first; cache only a measured hot path; queue only work that can be asynchronous with bounded backlog; consider read replicas only for demonstrated read bottlenecks/staleness tolerance; extract a service only when the benefit exceeds operational cost. Twelve-factor supports process scaling and attached caches/queues, but does not prescribe this order, replicas or microservices. [Statelessness](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/processes.md); [Process model](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/concurrency.md); [Resource examples](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/backing-services.md); [Trade-offs](https://learn.microsoft.com/en-us/azure/well-architected/what-is-well-architected-framework).

Existing systems map each row to current controls and documented applicability exceptions; acceptance does not mandate topology migration. Existing scheduled jobs are inventoried separately, not silently waived by a topology exception. These are proposed acceptance criteria, not completed checks. No new service split until this gate and section 1 are satisfied.

## 6. AI engineering layer

- **Existing local constraint:** [ADR-0001](ADR-0001-model-routing-via-litellm.md) remains Proposed and excludes new paid Grok API dependency. LiteLLM documents routing, timeouts, retries and fallbacks; those features do not confer provider entitlement or eliminate cost. Use only approved endpoints/model aliases; no API call was made for this research. [LiteLLM router](https://docs.litellm.ai/docs/routing).
- **Reference capability, not adoption:** xAI caches exactly matching starting messages automatically; keep stable instructions/schema before changing task input. Cache hits are not guaranteed, including under eviction/routing changes. Measure cached tokens and end-to-end cost rather than promise a saving. [Prompt caching](https://docs.x.ai/developers/advanced-api-usage/prompt-caching); [Cache mechanics](https://docs.x.ai/developers/advanced-api-usage/prompt-caching/how-it-works).
- **Reference capability:** structured outputs conform within supported schema features/limits. Some accepted keywords are best-effort, so independently validate and reject unsafe/incorrect business actions. A valid shape is not factual correctness or authority to execute. [Structured outputs and best-effort limits](https://docs.x.ai/developers/model-capabilities/text/structured-outputs).
- **Proposed policy:** bounded tasks, fixed regression fixtures and cost/latency/quality comparisons before router or prompt changes. LeanCTX offers structural/context views and recovery paths; use exact source reads for evidence. [UNSOURCED] Project-specific LeanCTX/model-routing savings and eval thresholds are unmeasured here; do not quote a percentage. [LeanCTX upstream README](https://raw.githubusercontent.com/yvgude/lean-ctx/b14bf2f995119615e14190c50aee079fd6967f1c/README.md); [Measure a defined objective](https://sre.google/sre-book/service-level-objectives/).

## 7. Agent-operable repository

- **Facts:** Cursor documents `AGENTS.md`, scoped `.cursor/rules/*.mdc` rules, and skills with `SKILL.md` plus name/description. **Proposed policy:** keep safety/build/test instructions short in `AGENTS.md`; put scoped rules and optional workflows in their proper files. Rules are guidance, not the sole security control. [Rules and AGENTS.md](https://cursor.com/docs/rules.md); [Skills](https://cursor.com/docs/skills.md).
- **Proposed policy:** provide one command **or a small documented set per deploy unit/lane**, covering formatting, types, contract/module tests and secret-safe checks; run the equivalent lane set in CI. Starter maps `npm test` to `bash scripts/validate.sh`; ModMe documents `yarn verify:forge` and `yarn verify:generative`, not a mandatory single-root command. [Starter scripts](/workspace/thunderstone-starter/package.json); [ModMe verification lanes](/workspace/modme-ui-01/AGENTS.md#L29). CLI supports terminal/print automation; cloud agents run isolated development environments. No assumption that a local/global skill or file is automatically available remotely. [CLI](https://cursor.com/docs/cli/overview.md); [Headless mode](https://cursor.com/docs/cli/headless.md); [Cloud agents](https://cursor.com/docs/cloud-agent.md); [Skill locations/sync](https://cursor.com/docs/skills.md).
- **Cloud-hook gate:** cloud agents **must not depend on `sessionStart`**: the official matrix lists it as unavailable, not merely delayed. Use a reviewed task-entry bootstrap before writes, supported `beforeSubmitPrompt` for prompt validation, `afterFileEdit` for edit checks and `stop` for final evidence as appropriate; none replaces CI/approval gates or runs during early read-only turns. Self-hosted Pools/My Machines have a different documented lifecycle and can fire `sessionStart`; do not conflate them with cloud VMs. Config uses `timeout` (seconds), not `timeoutSec`; see the [hooks pattern](PATTERN-config-env-event-only-hooks-20261110.md#official-hook-schema-and-runtime-gate). [Cursor hook schema/matrix](https://cursor.com/docs/hooks.md).
- **Proposed policy:** required checks and reviews before merge; no bypass, force-push or review dismissal. **Never push directly to `main`; work on a branch/PR.** Commit/push/merge/deploy/migration require DT's own explicit approval words and routing through Git-Scout for git operations; quoting a framework is not permission. [Starter main-branch rule](/workspace/thunderstone-starter/AGENTS.md#L27); [DT standing gates](/workspace/thunderstone/artifacts/ARCH-FRAMEWORK-SWE-REVIEW-20261110.md#conflicts-with-dt-standing-rules). GitHub documents protected branches and plan limits; Origin documents Rules and Protections, PR reviews/checks and external CI apps. Choose by verified controls, not guessed parity. [Hosting ADR](ADR-0002-code-host-origin-vs-github-20261110.md). [GitHub controls](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); [Origin settings](https://cursor.com/docs/origin/settings.md); [Origin PRs](https://cursor.com/docs/origin/pull-requests.md); [Origin apps](https://cursor.com/docs/origin/apps.md).
- **Current-host nuance:** both inspected repos are public and user-owned (`owner.type: User` in archived first-party metadata). Public Free-repo branch protection availability differs from private-repo paid-plan requirements, and GitHub's “restrict who can push” feature is documented for organisation-owned repos; do not promise that control on these personal repos. Live rules/settings remain unverified and DT-owned. `skip-review`/draft behaviour skips an AI review under the starter policy, **not** required protection/review/check gates. [ModMe metadata](/workspace/thunderstone/artifacts/arch-framework-swe-sources-20261110/modme-ui-01-metadata-mcp.txt); [Starter metadata](/workspace/thunderstone/artifacts/arch-framework-swe-sources-20261110/thunderstone-starter-metadata-mcp.txt); [Protection availability and owner restrictions](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); [Starter review policy](/workspace/thunderstone-starter/docs/github-review-policy.md).
- **Gate:** a fresh, authorised checkout can discover instructions, dependencies, test command and evidence path. Briefs state paths, acceptance criteria and write approvals. These remain draft repo requirements; this task installed nothing. [Focused instructions](https://cursor.com/docs/rules.md); [Deterministic setup](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/dependencies.md).

## 8. Operability and cost

- **Proposed policy:** emit structured JSON-line events to stdout with task/release/correlation ID, outcome, latency and cost units; redact secrets and sensitive prompts. Runtime collectors own routing, retention and access. Twelve-factor requires streams, not JSON specifically; JSON/redaction are our overlay. [Logs as streams](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/logs.md).
- **Proposed policy:** alert on user-impact SLO burn and budget consumption, not noise alone. Agree a financial ceiling and approval path; separate subscriptions, model tokens, CI minutes, storage, egress and review-bot charges. No numeric ceiling assumed. [Multiwindow burn alerts](https://sre.google/workbook/alerting-on-slos/); [Cost and quality trade-offs](https://learn.microsoft.com/en-us/azure/well-architected/what-is-well-architected-framework); [Cursor usage billing](https://cursor.com/docs/models-and-pricing.md); [GitHub plans](https://github.com/pricing).
- **Proposed policy:** trigger bounded work from lifecycle/source-control events only; no cron, scheduled reminders or recurring polling jobs. Hook support varies by runtime; cloud hooks do not run during early read-only turns and `sessionStart` is unavailable in cloud agents altogether. Existing schedules require an explicit owner decision under the hooks-pattern inventory; do not claim blanket compliance or disable security/index jobs through this draft. Never rely on a hook as the only approval/security gate. [Runtime support caveats](https://cursor.com/docs/hooks.md); [Source-control triggers](https://cursor.com/docs/origin/agents.md).
- [UNSOURCED] Target-runtime scale-to-zero support, cold-start latency and minimum billing have not been established. Treat scale-to-zero as an experiment gated by section 1, not a promised saving. Fast startup/disposability remain useful independently. [Startup and stop behaviour](https://raw.githubusercontent.com/twelve-factor/twelve-factor/3ad5a5f36312cc8ad876abae1bd691acd790d4d1/content/disposability.md).

## 9. Pattern loop
