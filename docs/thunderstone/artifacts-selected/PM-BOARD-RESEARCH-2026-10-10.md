## Q2 — GitHub Projects v2 + Actions references (official)

- **actions/add-to-project** (not archived; last push 2026-09-29): inputs `project-url` (`https://github.com/orgs|users/<owner>/projects/<n>` — user projects supported), `github-token` (PAT with `repo`+`project`), optional `labeled`/`label-operator`. Events: issues opened/reopened/transferred/labeled; pull_request opened/reopened/labeled. It **only adds**; it does not set Status. https://github.com/actions/add-to-project
- **Automating Projects using Actions** (official): `GITHUB_TOKEN` is repo-scoped and **cannot access projects**; use a GitHub App (recommended for org projects) or PAT (recommended for user projects); sample uses `addProjectV2ItemById` then `updateProjectV2ItemFieldValue`. https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions
- **GraphQL** (official): classic PAT needs `project` (or `read:project` for reads); installation token also allowed. Look up field id and single-select option ids via `node(id: PROJECT_ID){... on ProjectV2{fields(first:20){nodes{... on ProjectV2SingleSelectField{id name options{id name}}}}}}`; set with `updateProjectV2ItemFieldValue(input:{projectId,itemId,fieldId,value:{singleSelectOptionId}})` or `value:{text:"..."}`. Cannot add and update an item in the same call. `addProjectV2ItemById` on an existing item returns the existing item id (idempotent). **Assignees/labels/milestone are issue properties, not project fields** — change with `addAssigneesToAssignable` etc. https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects
- **Tokens / ownership** (official statement): fine-grained PATs do **not** support "Projects owned by a user account"; fine-grained Projects permission and REST `/orgs/{org}/projectsV2` endpoints are organisation-only. https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens . Consequence for `users/Ditto190/projects/2`: **classic PAT with `project` (+`repo` if private repo items) is the only documented token**. GitHub App installation tokens on user-owned projects: community reports of "Resource not accessible by integration" (secondary sources, not an official statement): https://github.com/cdubiel08/ralph-hero/issues/1036 , https://github.com/damien-robotsix/robotsix-cai/commit/3d8975a867cdf8c687770e3336d212f565526b3e . ## Q3 — Gaps and recommendations

**Dependencies / blocked-by.** GitHub now has native issue dependencies ("blocked by"/"blocking"), shown with a Blocked icon on boards; CLI: `gh issue create --blocked-by`, `gh issue edit --add-blocked-by/--remove-blocked-by`, `gh issue view N --json blockedBy,blocking` (official: https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies). Sub-issues/Parent issue fields already exist on the board. A custom "Blocked by" text field would duplicate this and drift. Use native dependency as truth; use **Status=Blocked + Note** for non-issue blockers (waiting on DT, external). GraphQL field names for dependencies not verified this session.

**Claim locking.** Facts: GitHub assignment is additive (`addAssigneesToAssignable`); I found no documented compare-and-set / If-Match on assignees or project field writes, so two bots can both "succeed". Project field writes are last-write-wins. Inference (not tested): races are real. Critical point: if all bots authenticate with the same GitHub user/PAT, **assignee cannot tell bots apart** — the `Bot` text field is the only distinguishing mark and it is last-write-wins. Proposed protocol (untested): (1) candidate reads item; must be Status=Not started, no open blockedBy; (2) post an issue comment `claim bot=<name> nonce=<uuid>`; (3) re-read comments — **lowest comment id carrying a `claim` marker wins** (comment ids are server-ordered, giving a CAS-like tiebreak); losers delete/ignore their claim and pick another item; (4) winner sets Bot=<name>, Status=In progress (and assignee if distinct accounts exist); (5) release = Status back to Not started + Bot cleared + `release` comment. Add a `Claimed at` date field (or parse comment timestamp) so stale claims can be detected, mirroring `br coordination status`. Do not rely on labels as locks (same add-only race).

**Agent-readable export.** `gh project item-list 2 --owner Ditto190 --format json -L <n>` (default limit **30** — silent truncation trap; always pass `-L` and compare to `totalCount`), `--query "-status:Done -status:Archived"` for filtering, `--field` for extra columns (https://cli.github.com/manual/gh_project_item-list). For ids (field/option ids, item ids) use the GraphQL snapshot above and cache them in a config file; re-fetch on 'option not found'. Ready-work query = Status:Not started ∧ open ∧ no open blockedBy ∧ Bot empty — a ~30-line script, no new store.

**Environment note:** on the shared box, `gh project …` subcommands hung emitting "CURSOR_API_KEY missing from secret store" spam (wrapper/shim behaviour, not investigated); `gh api` and `gh api graphql` worked. Bots should call `gh api graphql` or test `gh project` first with `timeout`.

### Verdict on beads/Dolt layer
**Not worth adding now.** Cost/complexity: new binary + Dolt/SQLite store, server mode needed for true multi-writer (embedded is single-writer), schema-migration/upgrade steps, JSONL export is only derived, and `bv`/`br` explicitly say not to mix `bd` and `br` on one workspace. Fit: it creates a second source of truth competing with "GitHub is canonical for code-tied work"; sync between beads and GitHub issues would be our code to own. Its real gains (atomic claim, ready query, graph analytics) can be approximated on GitHub with native dependencies + the comment-id claim protocol + a small script. Revisit if: >~50 concurrently active items, need for graph analytics (critical path), offline/local-first agent work, or claim collisions actually occur despite the protocol. If trialled, keep it local/stealth (`bd init --stealth`, git-free) as per-agent scratch, never canonical.

## Ranked recommended changes (max 8)
1. **Token**: use a classic PAT (`project` + `repo`), stored as a repo secret, short expiry + rotation note; do not plan on fine-grained PAT or GitHub App while the board is user-owned. Alternative: move board to an org to unlock Apps, fine-grained PATs and `projects_v2_item` webhooks.
2. **Lean on built-in workflows first**: keep closed→Done and PR-merged→Done; enable "item added → Not started" and auto-add for `thunderstone-starter` (verify availability on user projects in the UI). Only use Actions for what built-ins can't do (PR opened → In progress, set Bot).
3. **Actions workflow** (via PR for DT review): `actions/add-to-project` + a `gh api graphql` step using cached field/option ids; PR opened → In progress; guard against fork PRs (secrets unavailable — general GitHub behaviour, not re-verified).
4. **Blocked-by**: standardise on native GitHub issue dependencies; Status=Blocked + Note for non-issue blockers; document in the skill.
5. **Claim protocol**: adopt the comment-id first-wins claim + Bot field + Status flip; document release/stale rules; add `Claimed at` date field.
6. **Ready/export scripts**: commit a `board-snapshot` + `board-ready` helper (always `-L` + totalCount check; fall back to `gh api graphql` if `gh project` hangs).
7. **Hygiene**: single canonical title convention (emoji prefix is fine but keep a Status/Bot field as truth); optional auto-archive of Done items after N days (archived items still count toward item cap per secondary sources).
8. **Beads/Dolt**: defer; set explicit revisit triggers (above).
